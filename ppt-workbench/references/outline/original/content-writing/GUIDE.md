# Content Writing Skill

## 目标与责任

outline 阶段把已确认的主题、受众、目标、逻辑框架和素材，组织成“简化 JSON（即简化页面 JSON）+ 整册 Markdown 说明”。这里不制作页面，也不写完整逐页文案。

主 Agent 是两个大纲文件的唯一写作者。研究助手可以补公开来源、素材摘要和图片候选，但不能改写大纲、提交确认、切换阶段或接管用户对话。

本 Skill 提供业务判断方法，不是固定工具调用顺序。你自行决定需要读什么、是否补证据、如何组织章节以及调用哪些当前可用能力；不要因为某个能力可用就机械调用。

## 双文件合同

写 JSON 前读取 `outline/draft/outline.example.json`，并以它为字段基线。

```json
{
  "topic": "演示主题",
  "sections": [{
    "title": "章节标题",
    "pages": [{
      "type": "content",
      "title": "结论性页面标题",
      "content": "概要：……\n写作要求：……\n证据：……\n素材：路径#锚点",
      "background_color": "#F7F8FA",
      "theme": "专业、可信"
    }]
  }]
}
```

- `outline/draft/outline.draft.json` 保存页面结构。概要、写作、证据和素材要求统一写入 `content`；背景图、背景色和主题使用独立字段。
- `outline/draft/outline.md` 只提炼整册结构、内容框架与论证思路、视觉设计理念、跨页一致性和素材原则，不逐页复制 JSON。
- 页面 ID、页码、状态、版本、会话归属和卡片字段由代码补齐。
- 可选路由信号 `page_role_id`、`business_pattern_candidates`、`data_shape_hint`、`visual_mode_hint` 只在判断明确时填写，不锁定具体 layout。

结论性概述必须先写入对应文件。不要在聊天正文里手写大纲总览表、页标题列表、章节定位说明或内部处理过程。

## 页面边界

- `cover`：封面页，必须出现；只有标题必填。
- `agenda`：目录页，必须出现；只列章节项。
- `introduction`：只用于 2-4 个短介绍项；复杂表达改为 `content`。
- `content`：正文页，默认页型。
- `section_divider`：长章节需要阅读节奏时使用。
- `summary` / `closing`：总结和结束页。

用户要求的总页数包含封面、目录、章节过渡和结束页。固定页不补正文证据，不为满足密度而硬塞内容。

## 判断方法

### 结论先行

每章和每个正文页都要回答“这一页要证明什么”。标题尽量是判断句，而不是“业务概况”“问题分析”这类话题词。

### 证据驱动，不是文字流畅度驱动

先看这一页要证明什么，再决定需要什么证据，是业务指标、用户反馈、市场数据、案例、政策还是权威来源，然后再匹配 Foundation 和素材锚点。

- 在 `content` 中用 `证据：...` 写明需求，用 `素材：路径#锚点` 标出可读素材。
- 找不到证据时写 `证据缺口：是`，不要硬编一个数字或用空泛表达蒙过去。
- 公开数据必须保留 URL、发布方、时间。
- 图片需求要写清用途和语义。背景图可写入 `background_image`；受控素材 ID、binding、来源和许可由工具结果或 support 文件保存，不把裸外链塞入草稿。

### 章节按叙事切分

章节应该承担清晰的叙事角色，章与章之间有递进、对照或因果关系。只有一两页的章节通常可以合并；超过 6-8 页正文的章节通常需要拆分。

### 与 Foundation 对齐

提交前检查主题、受众、沟通目标、逻辑框架、页数和素材边界是否真正落实到章节与页面中。对 `forbidden_claims` 不得越界；对 `evidence_gaps` 要在相应页面明确处理。

## 何时使用辅助能力

- 已有材料能支撑结构时，直接写大纲，不为“流程完整”额外检索。
- 缺公开来源、事实核验或图片候选时，再选择检索或研究协作能力；主 Agent 根据结果统一取舍和落稿。
- 页面角色、业务模式或证据结构拿不准时，再读取相关 Skill；方法建议不能替代当前 deck 的业务判断。
- 只有关键上下文缺失且会改变结构时才向用户提问，不重复询问已经确认的 Foundation。

## 提交出口

`outline_confirm()` 是零参数提交出口。它会自行读取并检查 `outline.draft.json` 与 `outline.md`，执行 preflight，并在成功时展示大纲确认卡。

两个文件完成后即可调用。若返回 `errors` 或 `missing_info`，按具体问题修正相应文件再提交，不要原样重试。确认卡出现后停止输出；用户通过卡片定稿后，后端自动进入下一阶段。

如果运行时在一次 Agent 结束后发来文件检查结果，只补其中尚未完成的部分。已经通过的文件不重写，修复后仍通过同一个提交出口收尾。
