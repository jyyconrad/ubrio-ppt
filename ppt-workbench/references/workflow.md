# 组合工作流建议

本文件只在用户要从材料、主题或数据得到一套 PPT，或明确要求搜集素材、整理大纲、按页/按批次生成时读取。它是工作方式建议，不是新的状态机、任务账本或跨宿主协议。Codex、Claude Code 等宿主已有批次、并行、任务恢复或工作流技能时，优先使用宿主能力。

## 推荐顺序

1. **素材整理**：读取用户授权的文件和范围，提取当前汇报需要的事实、数字、图片和来源，标注缺口、冲突、零值、公式缓存和扫描风险。没有外部文件时说明仅使用用户消息，不必虚构素材文件。
2. **大纲编排**：根据受众、场景和目标组织 `thesis`、`audience_decision`、`evidence_ladder`、canonical 清单与页序。每页用人话写清谁、场景、问题、动作、主观点和听众记住什么，再写 `proves`、主体形状、支撑证据、图表/图片建议和证据缺口。用户只要求直接生成时，大纲可以在内部完成，不必停下来等待确认。
3. **视觉系统与逐页简报**：先锁定整册 `visual_system`，再为正文页写 `visual_brief`。按 [全局视觉系统](visual-system.md) 把字体、配色、留白、图标、图表、背景和轻量装饰变成可执行规则；视觉样机只用来沟通构图，不能替代可编辑成品。
4. **整册预检**：多页任务把 deck contract 和逐页 spec 写入任务目录，运行 `scripts/validate_deck_contract.py`，再对全部 `page_spec.json` 运行 `scripts/svg/check_deck.py`。通过后再逐页生成；失败项先补证据、改页型或拆页，不能靠 `build_gold_svg_page.py` 的 placeholder 让页面进入 ready。
5. **逐页制作**：把当前页当作独立交付单元，读取当前页证据，选择页面方法，生成真实可编辑 PPTX，检查对象和容量，再进入下一页。具体方法见 [单页制作方法](page-generation.md)。
6. **整册交付**：宿主可以按自己的策略把页面组织成批次、并行任务或一个多页 PPTX。若产生多个 PPTX，再读取 `references/merge-export/guide.md` 合并；最终仍要检查用户将收到的那个文件。

## 多页与批次的建议

批次只是降低上下文和视觉检查压力的工作方式，不是用户必须理解的产物。可以按 2-4 页、内容相近或版式可复用来分组，也可以使用宿主已有的其他分批策略。无论如何调度，每页都要独立完成事实核对、源码/生成记录、对象检查和必要的预览；批次完成不能替代页面检查。

页面可以先后生成，也可以由宿主并行调度。并行时要为每页提供独立的输入证据和输出路径，避免多个任务覆盖同一 PPTX 或共享临时文件。合并前核对页序、页数、尺寸和页面缺失；合并后重新检查最终文件。

不要因为素材或大纲已经完成就把 PPTX 任务停在中间，也不要为了“完整流程”给只要求一页的用户额外制作整册。以用户请求决定范围，以每页的实际 PPTX 和检查结果决定完成度。

## 交接信息

如果宿主支持任务文件或工作区，建议保存以下信息，名称和格式由宿主决定：

- 素材来源和证据缺口；
- 大纲总论点、页序和每页页面种子（含人话四要素与主观点）；
- 整册 `visual_system` 与逐页 `visual_brief`；
- 当前页的标题、目的、证据、页面方法、资产和输出路径；
- 已完成页面、失败原因、修订次数和最终检查结果。

如果宿主没有这些能力，直接在当前任务中保留必要上下文即可。本技能不要求用户手写 JSON、manifest、receipt 或固定目录；多页任务的 deck contract 由模型/宿主保存在任务目录，供静态门禁复核。
