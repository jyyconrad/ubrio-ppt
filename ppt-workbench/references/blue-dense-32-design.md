# 32张参考图的逐页设计推理与实现建议

## 证据边界

本文依据32张静态图片的可见结果进行逆向推断，证据类型为`visual-only`。可以判断画面层级、构图、相对比例、阅读路径、可见组件和视觉编码；不能证明原PPT的母版、对象分组、占位符、图表数据、字体元数据、动画或原作者真实意图。下文“为何这样安排”均表示**基于画面的合理推断**，用于指导同布局、同风格、同密度的可编辑复刻。

实现基线：结构、关系、文字、图标和抽象图形使用SVG，经`write_svg.py → validate_svg_drawingml.py → render_svg_drawingml.py`转为DrawingML；有坐标轴、序列、图例或数据表的图表使用`native-chart-slot`；规则行列且需要编辑/排序的表格使用`native-table-slot`；SVG只画表题、外框、注释和关系，不用矩形/文本伪造原生表格。图标使用既有图标检索及`data-icon-id`。以下“槽”是内容合同，不是默认示例事实。

## R01 `汇报模板-p1.jpg`：三期价值递进

1. **业务问题**：研发效能升级为何值得持续投入，短期、中期、长期分别交付什么价值。
2. **版式推断**：阅读从左上标题进入，沿上升折线依次读三个时期，再下移到三类外部趋势，最后由底部深蓝条收束“理念—路径—终局”。上升线把时间与价值增长绑定；三阶段等宽使比较稳定，第三阶段位置最高，是视觉终点。
3. **文字配合**：标题先给“从效率到能力”的总判断；阶段标签回答时间，正文每期三条回答价值；趋势卡解释为什么现在要做；底栏不复述阶段，而把跨期规律压成三条管理结论。数字只用于时间窗口，不虚构成效。
4. **内容槽/容量**：标题1；章节引导1；阶段3×（时间标签1、价值点3、图标3）；趋势3×（名称1、解释2）；底栏3×（标签1、结论1）。
5. **实现与不可省语义**：SVG画折线上升箭头、三阶段区域、趋势卡和底栏；无原生图表。必须保留“阶段逐级升高”和“趋势解释阶段”的上下因果，不得退化为6张等权卡。

## R02 `汇报模板-p2.jpg`：铁三角、激励与能力

1. **业务问题**：组织推进为何必须同时具备业务、方法、技术三端，以及制度怎样支撑三端协作。
2. **版式推断**：左侧三块直边多边形围成中央小三角孔，先建立组织模型；右侧上下两排分别讲激励和能力，底部三原则横向验收。阅读顺序是“谁协作→怎样激励→怎样培养→用什么原则检查”。左图面积大，确保组织关系优先于政策清单。
3. **文字配合**：标题给三位一体结论；三块多边形内写角色责任；右侧卡写机制动作，不重复角色定义；底栏只写跨模块原则。蓝/青/紫让同一角色或机制在不同区域形成对应。
4. **内容槽/容量**：三端各名称+3行责任；激励3卡×3短句；能力3卡×3短句；底栏3条原则及一句解释。
5. **实现与不可省语义**：SVG画三块直边多边形、中央小三角孔、6卡和三色对应；图标嵌入。保留蓝/青/紫语义映射、环向互锁方向和“激励/能力”两层。责任白字完整落在各色块内。

## R03 `汇报模板-p3.jpg`：三阶段路线

1. **业务问题**：转型如何分阶段推进，每阶段的目标、动作、产出和风险是什么。
2. **版式推断**：顶部时间轴给全程方向，下面三张同高大卡让三个阶段按相同字段比较；底部价值箭头串联阶段结果。读者先看阶段，再纵向读一张卡，也可横向比较同一字段。
3. **文字配合**：标题说推进策略；副标题说总体演进；栏头给阶段和时间；四层正文分别承担目标、动作、产出、避坑，互不重复；大数字只出现在产出层，构成证据焦点。
4. **内容槽/容量**：阶段3×（时间/名称、核心目标1–2句、动作3、产出2–3项或大数、风险1–2句）；底部价值3段。
5. **实现与不可省语义**：SVG画时间轴、三卡外壳、字段图标与底部箭头；若产出需真实图表再开native chart，否则大数用DrawingML文字。四层字段不能合并，退出条件/风险不能省。

## R04 `汇报模板-p4.jpg`：举措到结果

1. **业务问题**：一年内做了哪些系统动作，产生了哪些可核验结果，经验是什么。
2. **版式推断**：标题先把两项最重要结果放大；背景窄带限制解释范围；中部4举措按顺序推进；下部5结果形成证据墙；底栏给经验。阅读是“结果吸引→背景校准→动作→证据→方法总结”。
3. **文字配合**：标题只放最强结果；背景给基线与约束；动作卡写做法；结果卡写前后值与洞察；底栏总结可迁移原则，不再列数字。
4. **内容槽/容量**：标题2个关键数；背景3条；举措4×（编号、名称、2–3行）；结果5×（指标、前值、后值、洞察）；经验1句。
5. **实现与不可省语义**：SVG画背景带、4步连接卡、5个数值卡和底栏；前后值可用文字/微型柱形。必须维持4动作对5结果的两层关系，不能让结果卡与动作卡混排。

## R05 `汇报模板-p5.jpg`：四类卡点诊断

1. **业务问题**：组织与机制的主要卡点分别是什么，表象背后的原因和对应方案如何区分。
2. **版式推断**：2×2让四类问题等权并列；每卡内部从上到下按“现象→根因→方案”，右侧独立洞察区做一句判断。阅读既可逐卡深入，也可横向比较同层字段。
3. **文字配合**：标题指出诊断目标；编号和卡题定义问题；现象写事实、根因写待验证解释、方案写动作；洞察把三层压成一个选择原则，不能复述方案。
4. **内容槽/容量**：4卡×（标题、现象1–2、根因2、方案2、洞察1）；每卡约7–9条视觉单元。
5. **实现与不可省语义**：SVG画4卡、三层色带、右洞察分栏；卡内若是规则字段无需native table。必须保留证据状态区别，不能把“根因假设”写成事实。

## R06 `汇报模板-p6.jpg`：指标体系与工具成效

1. **业务问题**：如何用设计、仿真、测试三类指标定位效率问题，工具升级带来什么可核验变化。
2. **版式推断**：上部三列各三行形成诊断矩阵，下部三张结果卡与上部列对齐。标题大数字吸引注意，随后读者可按列完成“指标→改善结果”的闭环。
3. **文字配合**：上部指标名+定义说明测什么；数值只在少数基线项强调；下部每卡给两项前后变化和一句洞察，避免重复上部定义。
4. **内容槽/容量**：类别3×（栏头、指标3×名称/定义/可选值）；结果3×（图标、变化值2、结论1）。
5. **实现与不可省语义**：SVG画三列、九行和结果卡；简单前后数可编辑文字，若需时间序列则native chart。每列必须有3项，且上下按类别对齐。

## R07 `汇报模板-p7.jpg`：双指标体系与案例闭环

1. **业务问题**：既要提高人效，也要约束资源配置；一个低效案例如何从现象走到成效。
2. **版式推断**：上半左右两组指标体系构成双目标，下半横向4步案例展示方法落地。先读制度性指标，再看案例验证，避免案例替代全局口径。
3. **文字配合**：标题给两项变化；每个指标行含定义/数值和右侧洞察，洞察说明管理用途；案例四步各承担事实、原因、动作、结果，不能互相重复。
4. **内容槽/容量**：两组×3行指标，每行名称、定义/值、洞察；案例4步×2–3条；首尾各1个大数/微图。
5. **实现与不可省语义**：SVG画双栏、行卡、4步楔形流程；结果微柱可SVG，真实序列用native chart。必须保留两个指标体系的边界以及案例的四段证据状态。

## R08 `汇报模板-p8.jpg`：设计降本方法与案例

1. **业务问题**：研发阶段如何前置控制成本，怎样度量，案例是否证明投入产出合理。
2. **版式推断**：三条水平分区依次回答“怎么做→怎么量→结果怎样”；4方法覆盖宽度，3度量略大，底部案例用大数字完成说服。
3. **文字配合**：标题给80%与1:27作结论；方法卡写动作，不写成效；度量卡给定义与洞察；案例区给事实、金额和比率，洞察解释而不重复数字。
4. **内容槽/容量**：方法4×名称+2行；度量3×名称+定义+洞察；案例动作3、结果4个大值、洞察1。
5. **实现与不可省语义**：SVG画三层标题分隔、方法卡、指标卡、案例框；金额/比率为文本，必要时原生表格承载明细。三层不能合成平铺卡阵。

## R09 `汇报模板-p9.jpg`：一库三平台

1. **业务问题**：研发数据底座与三个业务平台如何互通，联动带来什么价值。
2. **版式推断**：上部架构把“库”置左、“三平台”置右，以双向箭头强调交换而非单向供给；下部3案例按接口统一、管理可见、知识复用证明价值。
3. **文字配合**：标题给协同结果；架构卡写职责和交换内容；能力细条写共同机制；案例卡给任务、数值与洞察。洞察不得把样本外推为总体收益。
4. **内容槽/容量**：库1×2–4条；平台3×2–4条；双向接口4组；能力4项；案例3×（任务、结果、洞察）。
5. **实现与不可省语义**：SVG画架构、双向箭头和能力带；案例数值用DrawingML。必须保留稳定ID/版本在双向交换中的语义，不能画成四个独立系统卡。

## R10 `汇报模板-p10.jpg`：六指标与五层根因

1. **业务问题**：效率与质量是否同时改善，某个延期/缺陷如何逐层追到机制根因并闭环。
2. **版式推断**：上部六张同规格微图让读者扫描趋势；下部五层链把“看见偏差”转为“找到可改机制”；右侧整改闭环是行动出口。
3. **文字配合**：标题给综合评估原则；组标签区分效率/质量；卡内标题、主值、图、洞察各司其职；根因层级使用名词短语，整改写动作和验收，不重复根因。
4. **内容槽/容量**：指标6×（编号、名称、主值/阈值、4–5点序列、洞察）；根因5层×事实/解释；整改3条+复核条件。
5. **实现与不可省语义**：六个图使用native chart slot（柱/线），SVG画卡、洞察带、五层容器和箭头；整改为SVG。必须保留目标线、期次、五层递进及右侧出口。

## R11 `汇报模板-p11.jpg`：需求闭环与案例

1. **业务问题**：需求如何从多源输入变成可追踪价值，数字化闭环比传统传递改善在哪里。
2. **版式推断**：左上4功能建立平台能力，左中灰/蓝两列形成模式迁移，左下两项结果收口；右侧高卡独立承载案例证据。读者先理解机制，再验证案例。
3. **文字配合**：功能卡写输入/处理/输出；模式对照写相同维度的旧/新做法；左下两项量化结果用指标名和带单位的大数收口；右侧每行用大数+洞察解释业务意义。关闭/重开规则放在对应机制文字中。
4. **内容槽/容量**：功能4×3点；对照3行或可压缩的5维；量化结果2×（指标名、带单位的实际/目标/前后值）；案例3×（指标、主值、辅助值、洞察）。
5. **实现与不可省语义**：SVG画功能卡、模式面板、迁移箭头和案例外框；若对照为严格规则行列可用native table，但视觉上仍要保留灰→蓝面板。不能把右案例并入左侧普通卡。

## R12 `汇报模板-p12.jpg`：模块架构、根因与举措

1. **业务问题**：模块复用为什么低，架构与治理怎样共同提升复用和衍生效率。
2. **版式推断**：顶部金字塔先给三级架构；中部左右回答“为什么低/怎么做”；底部三结果证明落地。阅读遵循结构→诊断→行动→结果。
3. **文字配合**：标题给三项变化；金字塔每层写对象和示例；根因按机制/标准/工具分层；举措一一回应根因；结果卡用大数和洞察，不重复举措。
4. **内容槽/容量**：金字塔3层×名称/说明；根因3行；举措3条；结果3×主值/方向/洞察。
5. **实现与不可省语义**：SVG画分层金字塔、引线、根因表外壳、举措和结果；根因表规则数据建议native table。必须保留层级从基础到定制及根因—举措左右对应。

## R13 `汇报模板-p13.jpg`：七阶段门径

1. **业务问题**：研发七阶段如何设置门径，为什么并行和前置决策能降低周期与返工。
2. **版式推断**：顶部连续箭头建立全流程；中部两张机制图解释效率来源；底部三成效卡和右洞察将机制落到结果。深到浅渐变表现阶段推进。
3. **文字配合**：阶段写任务/交付物；甘特说明并行节省，成本曲线说明晚改代价；成效卡给前后值；洞察总结决策原则，不能复述数值。
4. **内容槽/容量**：阶段7×名称/图标/2行；甘特2种模式×7阶段；成本曲线6–7阶段倍率；成效3×前后值/小图；洞察3。
5. **实现与不可省语义**：SVG画阶段带、甘特条、曲线标注、成效卡；真实数据曲线可native chart。必须保留串并行对比和“越晚修改越贵”的单调增长语义。

## R14 `汇报模板-p14.jpg`：环境变化与四瓶颈

1. **业务问题**：为什么必须升级研发体系，外部节奏变化暴露了哪四个内部瓶颈。
2. **版式推断**：上部大面板用左证据、中央主图、右洞察形成“事实→变化→判断”；下部4列瓶颈解释组织障碍；底部深蓝条给升级定位。
3. **文字配合**：标题给环境判断；左三行提供不同维度证据；中央只突出一个主趋势；右洞察解释容错率；瓶颈写表现和量级；底栏给选择方向。
4. **内容槽/容量**：环境证据3；主图1组前后值；洞察1；瓶颈4×名称/2行/关键值；定位1。
5. **实现与不可省语义**：主柱图用native chart；SVG画证据行、洞察、瓶颈卡和底栏。不能把三组环境数据画成三个同权小图，否则偏离单焦点构图。

## R15 `汇报模板-p15.jpg`：屋顶式管理体系

1. **业务问题**：用户价值如何通过精益、数字工具、纵向层级和横向协同转化为研发效能。
2. **版式推断**：中心屋顶是价值目标，左右翼是两种方法，四层是管理纵深；左侧解释原则，右侧展示市场/制造协同，底部指标验证价值。阅读从屋顶向下，再左右扩展。
3. **文字配合**：标题给双轮驱动；屋顶写客户结果；两翼写方法差异；四层写职责和产物；左右侧栏写规则/接口；底部只放价值指标和核心洞察。
4. **内容槽/容量**：屋顶1+3短语；两翼2×3项；层级4×（名称、职责链、3个属性）；左原则2组×3；右协同2回路×4节点；底部5指标；洞察1。
5. **实现与不可省语义**：SVG画屋顶、四层、纵向双箭头、横向协同回路；无必须原生图表。屋顶、左右翼、四层和双侧协同缺一不可，不能仅保留四层架构。

## R16 `4d37d5950db6394b58249ca139ee7671.jpg`：Day 1与衰退预警

1. **业务问题**：客户驱动组织如何保持活力，哪些机制失效会进入衰退，如何提前识别。
2. **版式推断**：上半左循环说明健康模型，右链条说明退化路径；下半防御机制、活力曲线、预警信号三栏分别回答预防、趋势、监测。健康与衰退并置构成因果对照。
3. **文字配合**：标题给风险判断；循环节点写正常行为；衰退链写失效后果；下栏防御写机制、曲线写状态、信号写可观察证据，三者不互相复述。
4. **内容槽/容量**：健康循环4×3动作；衰退5×3表现；防御4×机制/工件；曲线2阶段+4正/4负特征+5信号；预警6×名称/说明。

5. **实现与不可省语义**：SVG画全部架构、节点、连接和虚线边界；记忆主列短期/推理为蓝色系，长期为青绿色，治理为橙色。下部关系节点另用类型配色：Message/Decision/Answer/Feedback/Evidence蓝，Entity/DocumentChunk青绿，ReasoningTrace/ToolCall紫，各节点保留独立图标。三列按固定条目数先分配行高，DocumentChunk、Feedback与各列总结带之间保留真实空隙；关系谓词只放在列间留白。画布固定3:2，关系谓词、回流线、系统边界、治理五条和底栏不能省，也不能强改16:9。

## 当前金标通用 builder 的不足

以下判断来自现有`ppt-workbench`入口与参考说明，不是对其未运行结果的猜测：`build_gold_svg_page.py`的定位是生成通过语义门的起始SVG，现有文档也明确通用布局不会自动实现复杂参考图的网格和连接。因此它适合普通卡片、简单对照、KPI起始页，却不足以单独生成这32类复合页面。

1. **骨架表达不足**：现有`layout`/`dominant`只能路由到较粗的卡片、对照、证据表等家族，无法声明“4+关口+4”“6指标+5层根因”“屋顶+两翼+四层+双协同”等固定组合。
2. **关系合同不足**：复杂页需要显式节点、边、方向、虚实线、回流、分支概率和门禁条件；通用`content_groups`不能保证关系数量和语义。
3. **容量门不足**：当前质量门能检查主张、证据和密度预算，但不会知道某参考必须有6周×5指标、6+5+5+4+4节点或6列Canvas，因此“ready”仍可能产出稀疏泛卡。
4. **混合对象编排不足**：一页常同时需要SVG关系图、多个native chart和native table；通用builder能发槽，但不会自动完成参考级的slot几何、z-order和跨组件对齐。
5. **特殊画布与派生视图不足**：R32固定3:2，R31必须由R10同源裁切；普通16:9逐页生成模型无法表达这两个合同。

## 32资源的接入原则

### 1. 作为参考资源包接入现有入口

建议在现有skill-graph和gold catalog下增加一个可发现的`blue-dense-32`参考家族，不新建平行技能入口。资源分三层：

- **DNA索引**：R01—R32的`reference_id`、选择条件、业务问题、画布比例、主要关系、固定组件计数、容量下限、适合/不适合场景。
- **空白骨架资产**：每个主页面保存无业务事实的`*.skeleton.svg`或参数化构图参考，只保留容器、关系、slot ID、对齐锚点和图标语义；R31声明`derived_from: R10`及裁切范围。
- **内容合同**：独立JSON schema/manifest片段定义每个槽需要的字段、数组长度、证据状态和连线清单，例如R25要求6/5/5/4/4节点及三行口径表，R27要求5条六周序列和约10节点根因树。

### 2. 选择条件必须是业务关系，不是外观关键词

Agent先判断页面要回答的问题和证据结构，再选R资源：有固定周度指标、Owner、行动、日期和根因树才选R27；有五层因果节点和多对多关系才选R25；有未来取舍、四象限、评分和概率分支才选R29。仅出现“蓝色、高密度、复盘、架构”等词不能命中具体骨架。

### 3. 在现有生成链中的位置

1. 正常建立`page_spec.json`，先完成主张、证据状态、来源和业务内容。
2. 路由命中R资源后加载DNA和内容合同，运行容量预检；字段不足时回到材料补齐，不用示例事实填洞。
3. 运行通用builder生成起始SVG和`native-data.json`，继承已有语义门、字体、主题、图标和overlay合同。
4. 用`scripts/svg/build_reference_page.py --describe R编号`读取相应构图的业务问题、内容角色和容量；将真实内容绑定到具名槽，由相应可编辑构图生成最终SVG与native sidecar。保留gold builder起始SVG，对比确认主观点和事实没有改变。
5. 对最终SVG再次运行DrawingML预检和渲染；视觉验收比较分区比例、组件计数、关系线、信息条数及R31/R32特殊画布。

### 4. 避免默认泛卡

- 命中R资源后，对最终预览核对本页列出的必要组件和关系；仍是通用等距卡网格或缺关键关系时继续修复，不能交付为复刻通过。
- 构图说明使用业务问题、阅读顺序、文字角色、必须保留的关系；几何函数实现稳定位置，Agent负责判断内容与关系是否适用。
- 容量检查需比较数组长度与骨架下限；正文过多允许压缩短句，少于下限则回材料，不自动删卡或放大留白。
- 多对多网络、概率树、泳道交叉线、逆向箭头、回流和门禁是“必需关系”，不得因布局困难静默降级。

### 5. 避免默认示例事实泄漏

- 构图说明与授权合成示例分开使用。`--describe`默认只给结构和字段；只有显式`--example`才给完整合成输入，示例不得替代用户真实材料。
- 生成默认必须提供完整`--content`；编译器核对字段/数组容量，缺项报错。`--example`仅用于用户授权的示例任务，产物记录为`synthetic_example`。
- `page_spec`中的每个数字仍必须来自当前任务canonical材料并带来源/周期/口径；资源只校验“需要几个数、什么类型”，不提供数值。
- 逐项把最终内容与当前输入核对，未知项保留未知。R31必须复用当前任务R10数据，不允许自行另造一组示例。关键词或禁词表不能证明证据没有泄漏。

## 验收原则

- 结构验收：画布比例、区域层级、组件数量、固定行列、关系线及阅读顺序与对应R一致。
- 语义验收：标题、标签、正文、数字、洞察各有不同职责；事实、假设、目标和建议状态清晰。
- 可编辑验收：SVG结构转DrawingML；真实图表和表格为原生对象；无整页图片冒充可编辑内容。
- 迁移验收：至少用一套不同业务内容验证资源，不出现原图事实或默认示例泄漏；能填满同容量，也能在内容不足时正确阻断。
- 视觉验收：逐R并排截图检查主焦点、分区占比、信息密度和特殊色彩；R31检查同源裁切，R32检查3:2、蓝/青绿/蓝的记忆主列、紫色推理轨迹与工具调用关系节点，以及橙色治理区。
